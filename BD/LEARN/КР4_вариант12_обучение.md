## 2. Предметная область: что мы моделируем

**Диссертация** — научная работа, которую автор защищает перед диссертационным советом. После защиты человек получает **учёную степень**:

- **кандидат наук** — после кандидатской диссертации;
- **доктор наук** — после докторской.

Степень всегда привязана к **разделу науки** (технические, экономические и т.д.), а сама работа — к **научному направлению** (конкретная специальность, например «05.13.01 Системный анализ»).

Задание просит автоматизировать типичные операции каталога диссертаций: красиво выводить ФИО, считать возраст, строить отчёты, находить «двойников» в базе, проверять корректность вводимых данных.

## 3. Структура базы данных (таблицы)

Схема описана в шаблоне сущностей (файл «Таблица Authors.docx»). В PostgreSQL имена латиницей, смысл — русский.

### 3.1. `authors` — авторы (соискатели)

| Поле | Тип | Зачем |
|------|-----|-------|
| `author_id` | INTEGER, PK | уникальный номер автора |
| `full_name` | VARCHAR | полное ФИО — для функции инициалов и поиска дублей |
| `birth_date` | DATE | дата рождения — для возраста и идентификации |
| `passport_data` | VARCHAR | серия и номер паспорта |
| `passport_issue_date` | DATE | дата выдачи паспорта — при объединении дублей оставляем запись с **более поздней** датой |

**Откуда взялось:** один человек = одна строка. Но в реальной жизни одного и того же человека могли завести дважды (сменил паспорт, опечатка) — для этого задание 2.2.

### 3.2. `science_sections` — разделы науки

Справочник: «Технические науки», «Экономические науки» и т.д.

| Поле | Смысл |
|------|-------|
| `section_id` | PK |
| `section_name` | название раздела |

**Связь:** один раздел → много направлений (`specializations`).

### 3.3. `specializations` — научные направления (специальности)

| Поле | Смысл |
|------|-------|
| `spec_id` | PK |
| `spec_code` | шифр, напр. `05.13.01` |
| `spec_name` | название направления |
| `section_id` | FK → `science_sections` |

**Откуда взялось:** диссертация защищается по **конкретной специальности**, которая входит в **раздел науки**. Именно `spec_id` используется в процедуре объединения дублей («по одному направлению»).

### 3.4. `dissertations` — диссертации

| Поле | Смысл |
|------|-------|
| `diss_id` | PK |
| `author_id` | FK → автор |
| `title` | название работы |
| `type` | `кандидатская` или `докторская` (может вводиться сокращённо — триггер исправит) |
| `spec_id` | FK → направление |
| `defense_date` | дата защиты |
| `approval_date` | дата утверждения в диссертационном совете |

**Связи (картинка в голове):**

```
science_sections ──< specializations ──< dissertations >── authors
                                              │
                                         authors_archive (история изменений автора)
```

### 3.5. `authors_archive` — архив изменений

| Поле | Смысл |
|------|-------|
| `archive_id` | PK |
| `author_id` | чей профиль меняли |
| `old_full_name` | старое ФИО |
| `old_passport_data` | старые паспортные данные |
| `change_timestamp` | когда произошло изменение |

**Зачем:** триггер задания 3.3 **не мешает** обновлению, но **сохраняет след** — кто и что было до правки.

## 4. Базовые понятия PostgreSQL, которые нужны для этой работы

### 4.1. Функция vs процедура

| | **FUNCTION** | **PROCEDURE** |
|---|-------------|---------------|
| Вызов | `SELECT format_fio('...')` | `CALL merge_duplicate_authors()` |
| Возврат | обязан что-то вернуть (`RETURNS`) | может не возвращать таблицу |
| Где результат | вкладка Data Output | часто `RAISE NOTICE` → Messages |

В задании процедуры могут выводить текст через **`RAISE NOTICE`**. Для pgAdmin мы **дополнительно** сделали функции/представления с табличным результатом — так удобнее смотреть данные.

### 4.2. PL/pgSQL — язык внутри PostgreSQL

```sql
CREATE OR REPLACE FUNCTION имя(параметры)
RETURNS тип
LANGUAGE plpgsql   -- ← процедурный язык
AS $$
DECLARE
    переменная INTEGER;   -- объявление
BEGIN
    переменная := 5;      -- присваивание через :=
    RETURN переменная;
END;
$$;
```

- `$$ ... $$` — «дollar-quoting»: можно писать код с одинарными кавычками внутри.
- `LANGUAGE sql` — функция = один SQL-запрос (проще, но без IF/циклов).
- `IMMUTABLE` — результат зависит только от аргументов (можно кэшировать).
- `STABLE` — не меняет базу, но может зависеть от `CURRENT_DATE`.
- `VOLATILE` — по умолчанию; может всё что угодно.

### 4.3. JOIN — соединение таблиц

```sql
FROM dissertations d
JOIN authors a ON d.author_id = a.author_id
JOIN specializations sp ON d.spec_id = sp.spec_id
JOIN science_sections ss ON sp.section_id = ss.section_id
```

**Зачем:** в одном запросе получить и автора, и название специальности, и раздел науки. Без JOIN пришлось бы делать несколько запросов.

### 4.4. Представление (VIEW)

```sql
CREATE VIEW v_authors_degrees AS SELECT ...;
```

**VIEW** — сохранённый запрос с именем. Открываете как таблицу: `SELECT * FROM v_authors_degrees`. Данные каждый раз считаются заново из базовых таблиц.

### 4.5. Домен (DOMAIN)

```sql
CREATE DOMAIN diss_type AS VARCHAR(50)
    CHECK (VALUE IN ('кандидатская', 'докторская'));
```

**Домен** — тип данных с ограничением. Любое значение, приводимое к `diss_type`, проверяется автоматически. Если не подходит — **ошибка**.

**Откуда в задании:** «проверка значений полей, для которых могут быть определены домены».

## 5. Домены (`01_domains.sql`)

### 5.1. `diss_type`

Допустимы только `'кандидатская'` и `'докторская'`.

**Как используется:** в триггере `trg_validate_dissertation` строка:

```sql
PERFORM NEW.type::diss_type;
```

Приведение `::diss_type` — это попытка «вписать» значение в домен. Если тип `'канд'` ещё не нормализован — упадёт. Поэтому **сначала** срабатывает `normalize_type_trigger`, **потом** `validate_dissertation_trigger` (порядок — по алфавиту имён триггеров: `normalize_...` раньше `validate_...`).

### 5.2. `past_or_today_date`

Дата не может быть **позже сегодняшнего дня**.

**Зачем:** дата защиты и утверждения не бывают в будущем. Проверка:

```sql
PERFORM NEW.defense_date::past_or_today_date;
```

## 6. Задание 1 — функции (`02_functions.sql`)

### 6.1. `format_fio(full_name)` — фамилия с инициалами

**Требование:** `"Иванов Иван Сергеевич"` → `"Иванов И.С."`; при ошибке → `'#############'`.

**Логика по шагам:**

1. Если `NULL` или пустая строка → `'#############'`.
2. Разбить строку по пробелам: `regexp_split_to_array(btrim(full_name), '\s+')`.
3. **3 слова** (фамилия, имя, отчество) → `Фамилия` + `И.` + `О.`
4. **2 слова** → `Фамилия` + `И.`
5. Иначе (1 слово, 4+ слов) → `'#############'`

**Ключевые функции:**

| Функция | Что делает |
|---------|------------|
| `btrim(s)` | убирает пробелы по краям |
| `left(s, 1)` | первый символ строки |
| `array_length(arr, 1)` | сколько элементов в массиве |

**Проверка:**

```sql
SELECT full_name, format_fio(full_name) FROM authors LIMIT 10;
```

**Примеры:**

| full_name | результат |
|-----------|-----------|
| Иванов Иван Сергеевич | Иванов И.С. |
| Петров Петр Петрович | Петров П.П. |
| Васильев Игорь | Васильев И. |
| Морозов | ############# |

### 6.2. `get_degree_full_name(d_type, section_name)` — полное название степени

**Требование:** тип `"докторская"` + раздел `"Технические науки"` → `"доктор технических наук"`.

**Логика:**

1. Сначала тип нормализуется через `normalize_diss_type` (чтобы `'док'` тоже понимался).
2. Если докторская → приставка `'доктор'`, если кандидатская → `'кандидат'`.
3. Название раздела переводится в **родительный падеж множественного числа** через `CASE`:

```sql
WHEN 'Технические науки' THEN 'технических наук'
WHEN 'Экономические науки' THEN 'экономических наук'
...
```

4. Склеиваем: `prefix || ' ' || suffix`.

**Почему не одна формула:** русское склонение нерегулярное, проще явный словарь.

**Проверка:**

```sql
SELECT get_degree_full_name('докторская', 'Технические науки');
-- доктор технических наук
```

### 6.3. `normalize_diss_type(raw_type)` — вспомогательная функция

**Зачем отдельно:** триггер нормализует только **новые** INSERT/UPDATE. Старые строки в таблице могли быть с `'канд'`, `'док'`. Эта функция нужна в SELECT и отчётах.

| Ввод | Вывод |
|------|-------|
| канд, канд., к.н. | кандидатская |
| док, док., д.н. | докторская |
| кандидатская | кандидатская |

### 6.4. `calculate_age(birth_date, target_date)` — возраст

**Требование:** возраст на `target_date`; если второй параметр не указан — на **текущую дату**.

**Сигнатура с DEFAULT:**

```sql
calculate_age(birth_date DATE, target_date DATE DEFAULT CURRENT_DATE)
```

**Формула:**

```sql
EXTRACT(YEAR FROM age(target_date, birth_date))::INTEGER
```

- `age(дата1, дата2)` — интервал между датами.
- `EXTRACT(YEAR FROM ...)` — сколько **полных** лет в интервале.

**Зачем в задании два поля:** вызывать для **даты рождения автора** и **даты защиты** — «сколько лет автору было в день защиты».

**Проверка:**

```sql
SELECT a.full_name,
       calculate_age(a.birth_date) AS сейчас,
       calculate_age(a.birth_date, d.defense_date) AS на_защите
FROM authors a
JOIN dissertations d ON d.author_id = a.author_id;
```

## 7. Задание 2 — процедуры (`03_procedures_and_views.sql`)

### 7.1. Отчёт по диссертациям за год

**Требование (структура вывода):**

```
Год
  Раздел1
    Направление1
      ФИО  дата  название   (сначала докторские)
      ФИО  дата  название   (потом кандидатские)
    Направление2
      ...
  Раздел2
    ...
```

**Параметр:** год защиты.

#### Табличная функция `fn_annual_dissertation_report(p_year)`

Возвращает **плоскую таблицу** — удобно в pgAdmin:

```sql
SELECT * FROM fn_annual_dissertation_report(2023);
```

**Как строится запрос:**

1. `FROM dissertations d` + JOIN авторов, специальностей, разделов.
2. `WHERE EXTRACT(YEAR FROM d.defense_date) = p_year` — только нужный год.
3. **Сортировка:**
   - `section_name` — по разделу;
   - `spec_name` — по направлению;
   - `CASE WHEN type = 'докторская' THEN 1 ELSE 2 END` — **докторские первыми**;
   - `defense_date`, `full_name` — внутри группы.

4. `format_fio(a.full_name)` — короткое ФИО в отчёте.

#### Процедура `get_annual_dissertation_report(target_year)`

Тот же отчёт, но **текстом** через `RAISE NOTICE` — как «иерархический» вывод в Messages:

```sql
CALL get_annual_dissertation_report(2023);
```

**Идея цикла:** переменные `current_section` и `current_spec` запоминают, что уже выводили. Если раздел сменился — печатаем заголовок раздела; если направление сменилось — заголовок направления.

**`IS DISTINCT FROM`** вместо `<>` — корректно сравнивает с `NULL`.

### 7.2. Поиск и объединение дублей авторов

**Требование:**

- Найти авторов, внесённых **дважды**.
- Идентификация: **одинаковые ФИО + дата рождения** (паспорт мог смениться).
- Если кандидатская и докторская по **одному направлению** (`spec_id`) — это **один человек**.
- Объединить: в `authors` одна строка с **более поздней** `passport_issue_date`.

#### Функция `fn_duplicate_authors()` / VIEW `v_duplicate_authors`

```sql
SELECT * FROM v_duplicate_authors;
```

**Как ищет пары:**

```sql
FROM authors a1
JOIN authors a2
  ON a1.full_name = a2.full_name
 AND a1.birth_date = a2.birth_date
 AND a1.author_id < a2.author_id   -- каждая пара один раз
```

**Поле `same_direction`:** есть ли у обоих диссертации с **одинаковым** `spec_id`:

```sql
EXISTS (
    SELECT 1 FROM dissertations d1
    JOIN dissertations d2 ON d1.spec_id = d2.spec_id
     AND d1.author_id = a1.author_id
     AND d2.author_id = a2.author_id
)
```

#### Процедура `merge_duplicate_authors()`

```sql
CALL merge_duplicate_authors();
```

**Алгоритм для каждой пары с `same_direction = true`:**

1. Сравнить `passport_issue_date` — кого **оставить** (`keep_id`), кого **удалить** (`remove_id`).
2. `UPDATE dissertations SET author_id = keep_id WHERE author_id = remove_id` — перепривязать все диссертации.
3. `DELETE FROM authors WHERE author_id = remove_id` — удалить дубликат.

**Важно:** если дубли по ФИО+дате рождения, но **разные направления** — процедура **не трогает** (это может быть однофамилец или ошибка оператора — нужна ручная проверка).

### 7.3. Список авторов с учёными степенями

**Требование:**

- Если кандидатская и докторская в **одном разделе** → только **«доктор ... наук»**.
- Если в **разных разделах** → через запятую: `'кандидат экономических наук, доктор технических наук'`.

#### Функция `fn_author_degree(author_id)`

**Шаг 1 — собрать факты одним запросом:**

```sql
bool_or(type = 'кандидатская')   -- есть ли кандидатская
bool_or(type = 'докторская')     -- есть ли докторская
MAX(section_id) FILTER (WHERE ...) -- раздел для каждого типа
MAX(get_degree_full_name(...)) FILTER (WHERE ...) -- текст степени
```

**`FILTER (WHERE условие)`** — агрегат только по подмножеству строк (PostgreSQL 9.4+).

**Шаг 2 — правило из задания:**

```sql
IF has_cand AND has_doc AND cand_section_id = doc_section_id THEN
    RETURN doc_degree;                    -- только доктор
ELSIF has_cand AND has_doc THEN
    RETURN cand_degree || ', ' || doc_degree;  -- обе через запятую
...
```

#### VIEW `v_authors_degrees`

```sql
SELECT * FROM v_authors_degrees;
```

**Примеры из вашей базы:**

| Автор | Степень | Почему |
|-------|---------|--------|
| Алексеев | доктор технических наук | канд + док, оба в технических |

## 8. Задание 3 — триггеры (`04_triggers.sql`)

### 8.1. Общая схема «как работает триггер»

```
Пользователь: INSERT / UPDATE / DELETE
        ↓
PostgreSQL вызывает триггерную функцию (RETURNS TRIGGER)
        ↓
В функции доступны OLD (старое) и NEW (новое)
        ↓
RETURN NEW  — операция продолжается
RAISE EXCEPTION — операция отменяется
```

| Момент | Когда |
|--------|-------|
| `BEFORE` | **до** записи в таблицу — можно изменить `NEW` или запретить |
| `AFTER` | **после** — удобно писать в другие таблицы (архив) |

### 8.2. Триггер 1 — `validate_dissertation_trigger`

**Требование:** проверить поля, для которых определены домены; даты защиты и утверждения не больше текущей.

**Что проверяется:**

| Проверка | Как |
|----------|-----|
| Название не пустое | `IF btrim(NEW.title) = ''` |
| Тип из домена | `NEW.type::diss_type` |
| Даты не в будущем | `::past_or_today_date` |
| Защита ≤ утверждение | `defense_date > approval_date` → ошибка |
| Автор существует | `EXISTS (SELECT 1 FROM authors ...)` |
| Специальность существует | `EXISTS (SELECT 1 FROM specializations ...)` |

**Тест (должна быть ошибка):**

```sql
INSERT INTO dissertations (author_id, title, type, spec_id, defense_date)
VALUES (1, 'Тест', 'кандидатская', 1, '2099-01-01');
-- ERROR: value for domain past_or_today_date violates check constraint
```

### 8.3. Триггер 2 — `normalize_type_trigger`

**Требование:** при добавлении заменить сокращения на полные значения.

**BEFORE INSERT OR UPDATE** — меняем `NEW.type` **до** сохранения:

```sql
NEW.type := CASE lower(btrim(NEW.type))
    WHEN 'канд' THEN 'кандидатская'
    WHEN 'док'  THEN 'докторская'
    ...
END;
```

**Тест:**

```sql
BEGIN;
INSERT INTO dissertations (..., type, ...) VALUES (..., 'канд', ...);
SELECT type FROM dissertations WHERE ...;  -- кандидатская
ROLLBACK;
```

**Порядок с триггером 1:** сначала `normalize_...`, потом `validate_...` — в validate уже приходит `'кандидатская'`, домен доволен.

### 8.4. Триггер 3 — `archive_author_trigger`

**Требование:** переносить в архив изменения сведений об авторах.

**AFTER UPDATE** на `authors` — когда меняются:

- `full_name`
- `passport_data`
- `passport_issue_date`

**Условие WHEN на триггере** — функция не вызывается, если эти поля не тронуты (экономия работы).

**В функции:**

```sql
INSERT INTO authors_archive (author_id, old_full_name, old_passport_data, ...)
VALUES (OLD.author_id, OLD.full_name, OLD.passport_data, ...);
```

Берём значения из **`OLD`** — как было **до** обновления.

**Тест:**

```sql
UPDATE authors SET passport_data = 'новое значение' WHERE author_id = 1;
SELECT * FROM authors_archive;
```

## 11. Частые ошибки и как их избежать

| Ошибка | Причина | Решение |
|--------|---------|---------|
| `type "diss_type" does not exist` | домены не созданы | сначала `01_domains.sql` |
| `'канд'` не проходит validate | normalize срабатывает после validate | имена триггеров: `normalize_` < `validate_` по алфавиту |
| Процедура «ничего не показывает» | `RAISE NOTICE` не на Data Output | смотреть Messages или `SELECT * FROM v_...` |
| `format_fio` даёт `#############` | не 2 и не 3 слова в ФИО | это ожидаемое поведение по заданию |
| Дубли не объединяются | разные `spec_id` | по условию объединяем только при same_direction |
| Кодировка в psql на Windows | консоль CP866 | использовать pgAdmin или `PGCLIENTENCODING=UTF8` |

## 12. Что могут спросить на защите

1. **Чем функция отличается от процедуры?** — функция в SELECT, процедура через CALL; процедура может не возвращать таблицу.
2. **Зачем домен, если есть CHECK на таблице?** — домен переиспользуется в нескольких местах и в триггере через приведение типа.
3. **Почему два триггера BEFORE на dissertations?** — один **исправляет** данные, второй **проверяет** уже исправленные.
4. **Почему archive — AFTER, а не BEFORE?** — архивируем **факт изменения**; OLD/NEW уже известны, основная строка уже обновлена.
5. **Как определяете, что два автора — один человек?** — ФИО + дата рождения + диссертации по одному `spec_id`.
6. **Почему при двух степенях в одном разделе остаётся только доктор?** — докторская включает кандидатскую по смыслу учёной карьеры в одной отрасли (формулировка задания).
7. **Что такое `FILTER` в агрегате?** — `MAX(...) FILTER (WHERE условие)` считает MAX только по строкам, где условие истинно.
8. **Что делает `age()`?** — возвращает интервал; `EXTRACT(YEAR ...)` даёт число полных лет.
